## 二、Samsung Finance Analysis 总体策略调整

Samsung Finance Analysis（SFA）现有 V1 已完成微信支付通知识别、微信与支付宝官方账单导入、Raw Evidence 保存、Canonical Transaction 生成、重复交易合并、人工复核和调试验证等基础功能。

但在进一步使用和分析后，发现单纯依靠系统通知获取支付信息存在较强的不稳定性，通知内容、系统权限、应用版本和厂商后台策略均可能造成漏记或识别失败。因此，项目后续不再仅围绕通知识别继续扩展，而是准备重新调整总体方案，重点研究多渠道数据采集、官方账单导入、截图与 OCR 识别、交易标准化及重复记录合并等能力。

目前主要调研了 BeeCount 和 AutoAccounting 两个开源项目。

### BeeCount

BeeCount 是一款较完整的个人记账应用，支持多账本、多账户、多币种、分类、标签、预算和周期记账，并可导入微信、支付宝及 CSV、TSV 等账单文件。项目还提供 OCR、支付截图、语音和自然语言辅助记账、本地 SQLite 存储、多种同步方式、Web 管理端和 MCP 接口。

其局限在于无法直接读取微信、支付宝内部交易数据，Android 自动记账仍主要依赖截图、OCR 或页面识别，可能出现漏记、误识别和重复记录。云端 AI 还涉及支付截图等信息发送至第三方服务的隐私问题，跨设备同步通常也需要额外部署或配置。

### AutoAccounting

AutoAccounting 是面向 Android 的自动记账数据采集项目，主要通过 LSPosed、LSPatch、OCR、通知、短信和 WebView 等方式提取金额、商户、时间及支付方式，再通过规则分类并发送给受支持的记账软件。

该项目提供了比单纯通知监听更多的数据采集思路，但不同方案均存在限制。LSPosed 需要 Root，可能影响系统安全、Samsung Knox 和金融应用兼容性；LSPatch 需要修改目标应用，可能遇到签名、登录和升级问题；OCR 模式无需 Root，但准确率和自动化程度相对有限。微信、支付宝及 Android 系统升级后，相关 Hook 点和识别规则也需要持续适配。

下一阶段将结合上述项目的功能和缺陷，重新梳理 SFA 的总体架构、数据来源和安全边界，再确定通知监听、官方账单、OCR、截图识别及其他采集方式在项目中的具体定位。

## 四、CC Switch 管理 Codex 中转站

7月30日至31日对 CC Switch 管理 Codex 中转站的配置逻辑进行了整理，重点明确了 Provider、会话历史、API 协议和认证方式之间的关系。

1. `model_provider` 与本地 Codex Session 历史记录相关。OpenAI 官方会话使用 `openai` 标识；开启“Codex 应用增强 → 统一 Codex 会话历史”后，CC Switch 会将本地 Session 的 Provider 统一标记为 `custom`，因此接入新的中转站时应使用：

   ```toml
   model_provider = "custom"

   [model_providers.custom]
   ```

2. CC Switch 本地路由仅在中转站上游不支持 Responses API、只支持旧版 Chat Completions API 时使用。若中转站原生支持 Responses API，则不需要开启本地路由。

3. 开启统一 Codex 会话历史并使用中转站时，需要在 `[model_providers.custom]` 中加入：

   ```toml
   experimental_bearer_token = "YOUR_API_KEY"
   ```

4. 不采用 OpenAI 官方认证时，需要配置：

   ```toml
   requires_openai_auth = false
   base_url = "https://sub2.congmingai.com"
   wire_api = "responses"
   ```

同时对 Codex CLI、Desktop 和历史 Session 的 Provider 标识问题进行了排查。Provider 名称或大小写不一致会影响历史会话的显示和恢复，因此后续应尽量由 CC Switch 统一管理相关配置，避免频繁手动修改 `config.toml` 和 `auth.json`。
